## Beam Search 在本题发挥什么作用

### 一句话回答

> **数学模型负责「描述问题」，Beam Search 负责「解出答案」。模型太复杂解不动，Beam Search 是那个能实际跑出结果来的算法。**

---

### 具体来说，它解决了什么

数学模型定义了四层东西：选哪个订单 → 在哪块料上放什么工件 → 放哪里 → 不够的采购。其中第二步和第三步（「工件怎么塞进 5 块原材料」）是 **3D 装箱问题**，NP-hard。

仅 $produce$ 变量就有大约：

$$5 \text{ 块} \times 7 \text{ 种工件} \times \text{每种几十个} \times 6 \text{ 种姿态} \approx \text{几千个 0/1 变量}$$

再加上每个工件的 $x,y,z$ 连续坐标和「两两不重叠」的析取约束，**不可能扔进求解器直接算出最优解**。

Beam Search 的作用就是**用启发式方法替代精确求解**，在可接受的时间（~30-60 秒）内给出一个接近最优的排产方案。

---

### 它替代了数学模型的哪部分

```
数学模型:
  select_h ─── 选哪个订单      → 人工枚举（3 个订单逐个算，最后比大小）
  produce    ─── 怎么排产       → Beam Search 接手 ← 核心
  emergency  ─── 不够怎么办     → 利润密度贪心（挤掉低价值工件）
  x,y,z      ─── 放在哪         → EMS 解码器（Beam Search 内部调用）
```

Beam Search 替代的是 **$produce$ + $x,y,z$** 这两个最难的决策——「在每个原材料块里放哪些工件、放哪里」。

---

### Beam Search 具体怎么解 3D 装箱

每一步的操作：

```
当前有 5 块材料（部分已放了工件，有剩余空间）
    │
    ├── 对每块材料的每个剩余空间，找出「当前能放入且最贴合」的 M=8 个候选工件
    │   （这叫 Best-Fit 评分，由 EMS 解码器计算）
    │
    ├── 对当前 K=10 个状态，每个状态 × 5 块材料 × 8 个候选 = 最多 400 个新状态
    │
    ├── 每个新状态 = 深拷贝旧状态 + 放入 1 个新工件 + 更新剩余空间
    │
    └── 400 个候选按利润排序 → 保留前 K=10 个 → 下一轮
```

循环到所有空间都塞不下任何工件为止。全程利润最高的那个状态，就是最终排产方案。

---

### 为什么是 Beam Search 而不是别的

| 候选算法 | 行得通吗 | 为什么不用 |
|----------|---------|-----------|
| **精确求解（MILP/CP）** | ❌ | 变量太多，商业求解器也跑不出来（NP-hard） |
| **纯贪心（K=1）** | 勉强 | 子问题一用了，没有回头路，早期一个错误选择堵死后续 |
| **随机重启贪心** | 还行 | 跑 20 次取最好，但仍然是在单条路径上碰运气，质量不稳定 |
| **穷举搜索（BFS/DFS）** | ❌ | 分支因子 ~40，深度 ~100，状态数 $40^{100}$，宇宙毁灭也算不完 |
| **遗传算法 / 模拟退火** | 可以 | 编码困难（3D 装箱的解不是向量，是工件序列 + 姿态 + 坐标） |
| **Beam Search** | ✅ | BFS 的剪枝版，K=10 在速度和质量间取得平衡，且结果确定可复现 |

---

### 一句话总结

Beam Search 在这道题里的角色就是：

> **把「NP-hard 的 3D 装箱」从「理论上描述得很漂亮但解不出来」变成了「30 秒内给你一个接近最优的生产方案」。**

它是数学建模竞赛的经典套路——模型归模型（告诉评委你懂了这个问题），算法归算法（告诉评委你真能把它解出来）。

---

### 为什么理论预测翻车了

理论体积分析有一个盲区：**假设所有工件一视同仁，按体积塞进去就行。** 但 Beam Search 用利润做选择标准，真实模拟了「逐利润择优排产」的实际行为：

| 假设 | 理论 | 实际（Beam Search） |
|------|------|-------------------|
| 工件优先级 | 按体积排列，同等对待 | **按利润排序，高利润优先占据好空间** |
| 低利润工件 | 剩余空间足够就能排下 | **排到时空间已碎片化，塞不下** |
| 利用率 | 假设达到子问题一的 98.28% | **实际 79-88%，因为碎片化** |
| 紧急采购 | 按利润密度补缺口 | **缺口远大于理论估计** |

理论分析的价值在于**粗筛**——快速排除明显不可行的方案；但最终的择优必须靠 Beam Search 实际运行，因为它捕捉了**几何碎片化**和**利润导向排序**之间的耦合效应。

---

### 最终结论

```
实际最优: H02，净利润 295,320
  - 先放 J05 锁住高利润，再放 J01+J02 填满空间
  - 紧急采购仅 J02×10 + J07×5，损失 10,500
  - 利用率 94.01%，接近理论上限

H01:     285,620（全自产，零风险，但利润不如 H02）
H03:     266,460（J06 被挤掉，紧急采购 32 个）
```

**H02 赢了。** 关键发现：Beam Search 的利润排序机制导致它错误地选择了 H01。多策略贪心通过尝试不同的放置顺序，发现"先放 J05→再放 J01/J02"的策略能让 H02 达到 295,320，超过 H01 的 285,620。论文里可以写：「单一的利润导向搜索会系统性排斥低利润密度工件，通过多策略探索可以发现更优的打包方案。」

对 H02 和 H03 分别用 K = 1, 5, 10, 20, 50 运行 Beam Search（M=8 固定）：

| 订单 | K | 净利润 | 紧急采购损失 | 利用率 | 耗时 |
|------|---|--------|-------------|--------|------|
| H02 | 1 | 216,240 | 50,040 | 79.27% | 0.1s |
| H02 | 10 | 216,240 | 50,040 | 79.27% | 1.6s |
| H02 | 50 | 216,240 | 50,040 | 79.27% | 8.9s |
| H03 | 1 | 266,460 | 32,000 | 87.85% | 0.1s |
| H03 | 10 | 266,460 | 32,000 | 87.85% | 1.5s |
| H03 | 50 | 266,460 | 32,000 | 87.85% | 8.1s |

**结论**：K=1 到 K=50 结果完全一致。这不是搜索宽度的问题，而是**利润排序机制的结构性缺陷**。

### 为什么 K 增大没有改善？

所有状态按总利润排名，高利润工件在任何分支里都会被优先放置。K 条路径在早期做出完全相同的高利润选择，实际上走的是同一条路。**早期根本没有分支敢选 J01（利润密度最低）——选了就会被利润排序淘汰。**

|------|------------|-----------|------|
| H01 | 285,620 | 285,620 | 0 |
| **H02** | 216,240 | **295,320** | **+79,080 (+36%)** |
| H03 | 266,460 | 266,460 | 0 |
| **总计** | 768,320 | **847,400** | **+79,080** |
| **最优订单** | H01 (错误) | **H02 (正确)** | — |
| **耗时** | 4.6s | **0.3s** | 15x 快 |

**核心发现**：多策略贪心通过尝试不同的放置顺序，突破了 Beam Search 利润排序的局限性。关键策略是"先放 J05 锁住高利润 → 再放 J01/J02 趁空间大填小工件 → 最后补其他"。

## 三、EMS 层（第 100-226 行）——最核心的几何引擎

EMS（Empty Maximal Space）是 3D 装箱的经典算法。这一层负责「在一个原材料方块里，维护剩余空间列表，放入工件，更新空间」。

### 3.1 Space 数据结构

```python
@dataclass
class Space:
    x: int; y: int; z: int       # 左下角坐标
    dx: int; dy: int; dz: int    # 三边长度
    def can_fit(self, dx, dy, dz):
        return self.dx>=dx and self.dy>=dy and self.dz>=dz
```

一个 Space 就是一个**空的长方体区域**。初始时每个原材料块只有一个 Space：`Space(0, 0, 0, 300, 200, 150)`。

### 3.2 `get_intersection(sp, ix, iy, iz, idx, idy, idz)` ——两个长方体求交集

```
空间 sp:  ┌──────────┐
          │          │
          │   ┌──┐   │  ← 工件 (ix,iy,iz, idx,idy,idz)
          │   └──┘   │
          │          │
          └──────────┘

返回值: (交集的 x,y,z, dx,dy,dz) 或 None（不相交）
```

这是一个纯几何工具函数：给定一个空间和一个工件的位置，算出工件与空间**重叠的那部分**。如果工件完全在空间外部（任一维度不交），返回 `None`。

**用途**：当工件放入某个空间后，其他空间如果和工件有交集，需要把交集部分从那些空间里挖掉。

### 3.3 `split_space(sp, rx, ry, rz, rdx, rdy, rdz)` ——被工件占据后，剩余空间怎么切

这是 EMS 最关键的操作。当在空间 `sp` 的坐标 `(rx, ry, rz)` 处放入尺寸为 `(rdx, rdy, rdz)` 的工件后，空间被切成**最多 6 块**：

```
        ┌─────────────────┐
        │      顶部        │  ← 工件上方的空间 (Z轴正方向)
        └─────────────────┘
        ┌──────┬──────────┐
        │ 前侧  │          │  ← 工件前后的空间 (Y轴方向)
        ├──────┤  工件    │
        │ 后侧  │          │
        └──────┴──────────┘
        ┌──────┬──────────┐
        │ 左侧  │  右侧    │  ← 工件左右的空间 (X轴方向)
        └──────┴──────────┘
```

代码 6 行对应 6 个方向，每个方向只在「有空隙」时才生成：

```python
if rz-sp.z>0:           # 工件底下有空间 (Z 方向)
    Space(..., rz-sp.z)  # 高度 = 工件底部 - 空间底部
if sp.z+sp.dz-rz-rdz>0: # 工件顶上有空间
    Space(..., 剩余高度)
if ry-sp.y>0:           # 工件前面有空间 (Y 方向)
    ...
# ... X 方向同理
```

**设计要点**：每个方向的厚度 = 工件侧边到空间边缘的距离。这保证了生成的子空间两两互不重叠，且完整覆盖了被挖掉工件后的所有剩余体积。

### 3.4 `merge_spaces(spaces)` ——空间合并（防碎片化）

当两个 Space 在某个维度上**完全对齐且相邻**时，合并成一个大空间：

```
合并前:  [空间A 100×50×30] [空间B 100×50×20]  ← X 对齐，Y 对齐，Z 相邻
合并后:  [空间AB 100×50×50]
```

代码检测三种合并场景：
- XZ 对齐 + Y 相邻 → Y 方向拼接
- YZ 对齐 + X 相邻 → X 方向拼接
- XY 对齐 + Z 相邻 → Z 方向拼接

每轮扫描所有空间对，直到没有可合并的对为止。合并只在空间列表过长（`> 150`）时触发——这是**懒惰策略**，因为合并本身也有开销，只在空间碎片化严重时才做。

### 3.5 `BlockPacker` ——单块原材料的打包器

```python
class BlockPacker:
    def __init__(self, dx, dy, dz):
        self.spaces = [Space(0, 0, 0, dx, dy, dz)]  # 初始：一整块空料
        self.placements = []                          # 已放工件列表
```

**`try_place(name, dx, dy, dz)`**——尝试放入一个工件，成功返回坐标，失败返回 `None`：

```
1. 找到所有能容纳该工件的空间
2. 选「间隙最小」的那个空间（Best-Fit 策略）
3. 从空间列表 pop 该空间
4. split_space() 把该空间切碎，生成新空间
5. 对其他所有空间，检查是否与工件相交：
   - 不相交 → 保留
   - 相交 → 切掉相交部分，保留剩余
6. 合并新旧空间列表
7. 如果空间数 > 150，触发 merge_spaces()
8. 记录放置
```

**为什么还要对其他空间做相交检测？** 因为 EMS 的空间不是完美隔离的——一个工件放在 Space A 里，可能同时伸进 Space B 的领地（Space A 和 Space B 在 XY 面相邻但在 Z 方向有重叠）。步骤 5 保证所有空间都被正确更新。

**`copy()`**——深拷贝整个 Packer。Beam Search 需要从同一个状态分支出多个子状态，每个子状态必须独立修改自己的 Packer，不能互相污染。这是整个 Beam Search 正确性的基础。

**`get_top_candidates(remaining_dict, M)`**——给定还需生产的工件（dict 形式），返回当前块中能放入的 top-M 个候选：

```
对每个还需生产的工件:
  对每种旋转姿态:
    在所有空间中找能容纳的
    选间隙最小的空间
    评分 = (空间长-工件长) + (空间宽-工件宽) + (空间高-工件高)
按评分升序（越贴合越好）
去重：同一工件只保留贴合度最高的姿态
返回前 M 个
```

这一步是 Beam Search 的**分支生成器**——它为每个 Packer 提供「当前最好放哪些工件」的建议。

## 四、状态层（第 228-248 行）

```python
@dataclass
class BeamState:
    packers: List[BlockPacker]   # 5 个 BlockPacker 的独立拷贝
    packer_names: List[str]       # ["L01_1", "L01_2", "L02_1", "L02_2", "L03_1"]
    placed: Dict[str, int]        # {"J04": 38, "J06": 15, ...}
    profit: int                   # 当前自产总利润
    depth: int                    # 已放置工件数（防止无限循环）
```

一个 BeamState 就是**排产过程中的一个快照**——5 块材料当前各自放了什么、还剩多少空间、还有哪些工件没做。

**`copy()`**——深拷贝整个状态。这是 Beam Search 最频繁的调用（每扩展一次就调用一次），所以必须高效：每个 Packer 单独 `copy()`，`placed` dict 和基本类型各自复制。

## 五、引擎层（第 251-384 行）——Beam Search 主循环

### 5.1 输入处理

```python
def solve_order_beam(order_name, order_demand, K=10, M=8, max_iterations=300):
    # need = {工件名: 还需生产数量}  ← 订单需求 - 库存
    need = {}
    for wp in WORKPIECES:
        d = order_demand.get(wp.name, 0)
        s = STOCK.get(wp.name, 0)
        n = max(0, d - s)
        if n > 0: need[wp.name] = n
```

`need` 只包含需要自产的工件（库存已扣除）。例如 H01 的 J03 库存 20、需求 24 → `need["J03"] = 4`。

```python

        min(STOCK.get(wp.name, 0), order_demand.get(wp.name, 0)) * wp.profit
        for wp in WORKPIECES
    )
```

库存利润是定值，不参与搜索，最后直接加上。

### 5.2 初始状态

```python

                  for m in AVAILABLE_MATERIALS for i in range(m.quantity)]
```

5 块材料各自一个 BlockPacker，初始都是空的。`beam` 是当前轮的 K 个最优状态。

### 5.3 主循环——三层嵌套

```python
    while beam and iteration < max_iterations:      # 外层：迭代轮次
        for state in beam:                           # 中层：遍历 K 条路径
            # 构建 remaining dict（移到 packer 循环外）
            remaining = {}
            for wp_name, needed_count in need.items():
                already = state.placed.get(wp_name, 0)
                if already < needed_count:
                    remaining[wp_name] = needed_count - already

            for pi, packer in enumerate(state.packers):  # 内层：5 块材料
                top_cands = packer.get_top_candidates(remaining, M)
                for score, nm, dx, dy, dz in top_cands:   # 最内层：M 个候选
                    new_state = state.copy()                # 深拷贝
                    new_state.packers[pi].try_place(...)    # 放入工件
                    new_state.placed[nm] += 1               # 更新计数
                    new_state.profit += WP_MAP[nm].profit   # 累加利润
                    candidates.append(new_state)            # 收集候选

        candidates.sort(key=lambda s: s.profit, reverse=True)  # 按利润排序
        beam = candidates[:K]                                   # 保留 top-K
```

**数据流**：

```
  beam (K 个状态)
     │
     ├─→ state[0] ─→ packer[0] ─→ candidate[0..M-1]
     │                       ─→ packer[1] ─→ candidate[M..2M-1]
     │                       ...
     │                       ─→ packer[4] ─→ candidate[4M..5M-1]
     ├─→ state[1] ... 同上
     ...
     └─→ state[K-1] ... 同上
                    ↓
          candidates (最多 K × 5 × M 个)
                    ↓
           按 profit 降序排序
                    ↓
           保留前 K 个 → 下一轮 beam
```

**关键设计决策**：

- **state.copy() 在每个候选内部调用**，而不是在 packer 循环外。这避免了不必要的拷贝（如果一个 packer 没有候选，就不拷贝）。
- **循环内提前退出**：`if not remaining: continue`——某个状态如果已经完成了所有工件，不再浪费计算。
- **best_state 是全局跟踪**：不是从最终 beam 里选，而是在每一轮 candidates[0] 中更新。因为中途某个状态可能利润最高但后期被淘汰（虽然不太可能），所以每轮都检查。

### 5.4 结果统计

## 八、关键实现细节问答

### Q1: `try_place` 里为什么先 pop 空间，再遍历其他空间做相交检测？

因为 EMS 的空间不是严格分区的——一个工件放在 Space A 的角落，可能同时伸进 Space B（两者在某个维度重叠）。如果只切 Space A 而不处理 Space B，Space B 里就有一个「工件占着但空间还认为空着」的区域，导致后续工件穿模。

步骤 5 的相交检测就是解决这个问题：对所有剩余空间，检查是否被新工件贯穿，贯穿了就切掉。

### Q2: `merge_spaces` 为什么阈值是 150？

经验值。空间数太少合并不划算（合并本身 O(n²)），太多则碎片化严重影响 `get_top_candidates` 的搜索效率。150 是在精度和速度间的平衡。

### Q3: `get_top_candidates` 为什么去重？

同一种工件的 6 种姿态可能都入选 top-M，导致 M=8 的名额被一种工件占满。去重保证 M 个候选对应 M 种**不同**工件，增加搜索多样性。

### Q4: 为什么 `best_state` 不在循环结束后从最终 beam 里选？

因为 beam 只保留当前轮的 K 个状态。有可能第 50 轮的某个状态利润很高，但在第 51 轮它的子状态全部无法扩展（空间满了），而其他状态继续。`best_state` 全程跟踪，确保不丢失中间的最优解。

### Q5: 时间复杂度到底多少？

文档里写的是 O(depth × K × M)，但实际每次扩展还包括：
- `state.copy()`：深拷贝 5 个 Packer（每个有空间列表 + 放置列表）
- `get_top_candidates`：遍历每种工件 × 6 种姿态 × 所有空间
- `try_place`：空间分割 + 相交检测

总耗时 ≈ O(depth × K × 5 × (工件种类 × 6 × 空间数))。实际中 depth≈200-300, K=10, 空间数≈50-100，总耗时 1-2 秒/订单。

### Q6: 为什么没有多线程？

Beam Search 每轮依赖上一轮的排序结果（选 top-K），各状态扩展可以并行但排序有依赖。Python GIL 下多线程收益有限，且代码复杂度大增。对竞赛场景，1-2 秒/订单已经够快。
